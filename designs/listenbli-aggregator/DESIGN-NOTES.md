# listenBli 聚合版 — 设计说明

三个交付物，按做出来的顺序：

1. **三方向对比画布** —— 决定「聚合」长什么样时看的那一版（`ListenBli Aggregator.html`）。
2. **混音台可点击原型** —— 方向 A 选定后做深的那一版（`ListenBli Mixer.html`）。
3. **聚合听歌（我的歌）** —— **当前版本**（`ListenBli Library.html`）。第 2 版的重心错了：
   它做的是「跨平台视频条目浏览器，顺带放音频」，而要做的是**听歌**。这一版换掉了中心。

> 第 2 版保留作对照，不再更新。它里面仍然有效的东西（队列、已下载、能力声明、来源详情）
> 都搬到第 3 版里了；被换掉的是**主屏**、**行内的平台标记**与**视频元数据**。

---

## 假设与上下文（读这份文件时请先看这里）

**产品**：把 listenBli 从「哔哩哔哩播放器」重做成**聚合音频播放器**。现在的实现是一个
`enum Source { Bilibili, Youtube }` 加 99 处 `match`，加第三个来源要改掉一大半；这一轮要
回答的是「多来源共存」在界面上长什么样，而不只是换个皮肤。

**已确认的前提**（来自本轮提问）：

| 项 | 决定 |
|---|---|
| 画布 | 1440 × 900 纯内容区，不带系统窗口外壳；可点击 hi-fi 原型 |
| 信息架构 | 「全部」聚合页 + 每来源 tab（B 站 / YouTube） |
| 视觉 | **全新方向**，先看 3 个方向对比，不由旧稿「深夜电台」延续 |
| 来源 | 只画真实的 B 站 + YouTube，不编造第三个来源 |
| 重点能力 | 跨源去重 · 来源管理与会话 · 统一队列与来源标识 · 跨源歌词标注 · 缓存与离线 · 连接器形态（六项全要） |

**设计上下文**：仓库里没有 design system（`designs/*/_ds_manifest.json` 为空）。最有力的
上下文是旧稿 `designs/listenbli-player/`（设计令牌、组件清单、15 张状态截图）与 Rust 源码
本身（`src/api/models.rs` 的 `Track`/`Source`/`AudioQuality`、`src/net.rs` 的 `DownloadPlan`、
`src/lyrics/` 的回退链）。旧稿保留不动，本方案另起目录，两者可对照。

**同一条红线**（三个方向都遵守）：**来源不能变成商标色大乱斗**。B 站粉与 YouTube 红若同时
作为界面主色，界面会碎成两半，第三个来源一来更糟。三个方向各自给出不同的克制解法 ——
这是它们真正的差别所在。

## 三个方向

### A · 混音台 SWITCHBOARD
**工业仪器感 · 深色。** 凌晨三点的播控台。

- **聚合的隐喻**：来源 = **输入通道**。调音台天生就是把多路输入合成一路监听，这正是
  「聚合」的字面意思，不需要解释。
- **来源标识**：通道字母 + 一颗 LED（`A` / `B`），**完全不用品牌色**。
- **配色**：暖石墨 `#08080a → #2d2d34`，琥珀 `#ffb454` 是唯一的「在播」信号色，
  荧光绿 `#5fd39a` 表示就绪/已缓存，红只用于错误。
- **字体**：`Archivo Narrow`（蚀刻式大写标签）+ `IBM Plex Mono`（读数）+ `Noto Sans SC`。
- **布局**：左侧竖向 **INPUT 条**（通道 LED、电平、缓冲条、连接器位），中间是监听汇聚
  列表，右侧 **LYRIC FEED**，底部是实体传输条 + 每通道缓冲表。
- **去重**：同一首歌在一行里用上下两枚通道标签表示；展开后第二条起回到同一行组内，
  左缘留一道竖导轨 + 每行一个横向刻度。
- **缓存**：直接复用调音台语言 —— 每通道一根缓冲条，行内 chip 上的 LED 表示该来源是否已缓存。

### B · 索引 THE INDEX
**编辑/印刷感 · 浅色。** 一本录音目录，不是一块屏幕。

- **聚合的隐喻**：来源 = **馆藏（collections）**，聚合页是**总索引**。索引天然处理
  「同一件东西有多个出处」—— 一条著录，两枚出处章。
- **来源标识**：细边框的**钞记（stamp）**，`B 站` / `YT`，只有墨色粗细的区别，不靠颜色区分。
- **配色**：暖纸白 `#f4f1ea`，墨黑 `#16150f`，发丝线 `rgba(22,21,15,.14)`。
  **浅色音乐播放器是反类型的** —— 这正是它的价值，与 A/C 一眼可辨。
- **朱红的语义**：全书只有朱红 `#c8452a` 这一种彩色，它只表示**「当前」**——正在播放的
  那一条著录、当前选中的目次入口、以及那个「在播」按钮。音质、来源、缓存一律用墨色，
  不用颜色（无损音质是加粗的墨，不是红色）。
- **字体**：`Newsreader`（标题衬线）+ `Archivo`（元信息）+ `Courier Prime`（编号/时长）
  + `Noto Serif SC`（中文正文，行高 1.9）。
- **布局**：左侧**目次**，六个能力就是六个章节（全部 / B 站 / YouTube / 队列 / 已下载 /
  接入来源）；中间是**编号著录列表**；右侧是歌词页，带「注一 / 注二」脚注。
- **去重**：合并态只列一条著录、出处栏并列两枚章；展开态按来源条目分行，重复的以
  **`参见 01`** 回指首次著录的编号 —— 目录学的传统做法。

### C · 潮汐线 TIDELINE
**有机/空间感 · 深色。** 一间能看见水深的暗房。

- **聚合的隐喻**：多条支流汇成**一条主流**。聚合页是一条被合并后的流，左缘的
  **支流轨**显示各路来水；合并是「已经发生过的事」，用一个汇入读数交代。
- **来源标识**：来源 = **色温**，只以一道极淡的细丝（filament）出现，配两字母标记。
  品牌色被稀释成氛围，不参与信息层级。
- **配色**：深蓝黑 `#06080d → #1d2534`，冷青 `#5ec8d8` 是强调，暖沙 `#e8c07d` 是缓存色。
  有颗粒与深度的渐变，但拒绝紫色光污染。
- **字体**：`Bricolage Grotesque`（标题，略带有机感）+ `Noto Sans SC` +
  `Spline Sans Mono`（数字）。
- **布局**：不对称。主流行居中偏右、行距舒展；底部播放条**压在**流行之上（玻璃浮层、
  负外边距）；队列以横向胶片形式横穿来源；右侧「声音」面板放歌词。
- **去重**：主流里只出现一次，行首是收束记号（两道细丝并成一条）；展开后第二条起以
  `汇入 01` 回指。
- **缓存**：用**深度**编码 —— 已缓存的行「沉」得更实（更密的底、落定的内阴影），
  行尾一列暖沙表示落盘进度（满 = 已完整缓存，半 = 部分缓存，空 = 未缓存）。

## 三个方向共用的对比开关

每个画板都有同一个开关：**「合并重复」开 / 关**。这是聚合最难的设计问题 —— 同一首
《晴天》在 B 站有 4K 修复版、在 YouTube 有官方 MV，合并成一条还是并列两条？三个方向
给出各自的答案形态，用同一个开关可以直接横比。

另外每个画板都固定展示这几处，保证对比是同题的：顶部来源 tab、跨源搜索结果、行内来源
标识、右侧歌词与出处、底部播放条与当前来源、队列预览、缓存状态、以及一个「接入来源」
的连接器入口。

## 第三阶段：
- 库列表 11 首歌比可用高度高 27px、右栏歌词窗口太长、搜索结果 14 条溢出 → 行高与窗口调准；
- 「加入」按钮被塞进 28px 的列里挤到换行 → 动作列加宽到能放下一个按钮；
- `.a-seg` 的分段格子被 flex 压扁，四个筛选标签挤成一串（调音台那几处因为标签短没暴露）
  → `flex: none` + `nowrap`；
- **筛选器一直是完全没有样式的** —— 因为 `.a-seg` 定义在 `mixer.css`，而 Library 不加载它。
  这是最值得记的一条：共用组件必须住在共用样式表里；
- B 站收藏夹里出现了 YouTube 独有的《青花瓷》、YouTube 点赞里出现了 B 站独有的《稻香》
  → 按各平台实际持有的版本重排歌单，本地歌单才允许放任何歌；
- 歌单详情只列 3 首、下面空一大块 → 补足条目并加一行「Showing 7 of 128 / 加载更多」；
- 来源详情里把「这首歌的全部版本」写成了「这首歌唱片的全部版本」。

第二阶段：混音台可点击原型（方向 A 已选定）

方向 A 之所以被选中，是因为「调音台把多路输入合成一路监听」这个隐喻**不需要解释**，而且
「来源 = 通道」直接给出了克制来源标识的办法（字母 + LED，不用品牌色）。

做深时加了一条组织原则：**硬件台子不用弹窗改变自己在做什么，它有页面键。** 所以
监听 / 队列 / 存储 / 输入 是主控段上的四个键，键后面的工作区整体切换，而**顶栏、通道电平、
底部传输条永远不动** —— 这正是聚合播放器需要的：换页不打断正在播的东西。

唯一占满整个界面的是「接入来源」：插入一个新模块是**对台子做的事**，不是台子上的一个页面。

### 四张新页面各回答什么

| 页面 | 回答的问题 | 关键设计 |
|---|---|---|
| **监听 MIX** | 跨源搜索结果怎么呈现 | 合并重复开关；切到单来源 tab 时**撤掉**合并开关（没有可合并的对象），并把它明确说成「这个来源自己的持有」 |
| **队列 QUEUE** | 跨源队列怎么管 | 每行自带通道字母、音质与**入队来源**（搜索/收藏夹/历史/下一首播放）；`下一首播放` 与 `移除` 是真的能用的；正在播的那条不允许移除；右栏是来源分布与交替次数 |
| **存储 STORE** | 缓存与离线怎么管 | 四根电平块（总计 / 通道 A / 通道 B / 歌词封面）；**半成品显式标成「仅前半」**并给整行一个警示底色，而不是和完整项长得一样；固定项与正在播放项永不被清理 |
| **输入 INPUT** | 来源与会话怎么管 | 每个来源一个展开的通道模块：会话（账号/匿名 + 凭据动作）、**能力声明**、音质优先级、作用范围（参与聚合/仅单独浏览/停用）；未声明的能力在列表里是暗的，并写明「不是空的页签，是直接没有」 |
| **接入来源**（浮层） | 「后续可能增加来源」怎么兑现 | 三步：基本信息（含通道字母占用检查）、**能力声明**（4 组 14 项，可勾选）、会话方式；底部实时回报「这份声明会让界面长出哪些品目」 |

### 能力声明是整件事的支点

原型里把「来源」建模成**一份能力声明**（`CAP_GROUPS` / `CAPS_BILIBILI` / `CAPS_YOUTUBE`）：
声明了什么，界面就长出什么。这不是装饰 —— 现在源码里「收藏夹/历史只在 B 站出现」是硬编码
分支，而在这份设计里它是**声明的自然结果**。输入页右栏那张「声明项 → 长出的界面」表把两个
来源的 14 项逐项对照，连**两家都没声明的「分区 / 榜单浏览」**也照实显示为未声明 —— 那正好
对应 README 里「未实现分区浏览」这条已知限制。

## 第三阶段：听歌 re-cut（当前版本）

一次方向修正带来的重做。原话是「我是想做一个**听歌**的聚合 app」—— 第 2 版列表里塞的是
UP 主、播放量、「合集 75:32」、「【4K修复】」，那不是听歌，那是拿视频条目当第一公民。

**新的重心**（三个问题定下来的）：

| 问题 | 决定 |
|---|---|
| 打开看到什么 | **我的歌**为主屏，右栏常驻**正在播放**（封面 + 歌曲事实 + 歌词）。搜索降为入口 |
| 「聚合」合什么 | **合并「我的歌」**：跨平台的收藏与歌单汇成一个库。同一首歌的多平台版本去重降为**基础设施** |
| 平台露多少 | **默认完全不露**；平台、音质、原链接只在「来源」详情里可查 |

### 因此冒出来的三个新问题，和它们的答案

**1. 一首歌在库里出现几次？**
一次。库里 214 首是「合并后」的数：B 站收藏的晴天和 YouTube 点赞的晴天是同一条。
列表里没有平台标记 —— 一行就是一首歌：歌名 / 歌手 / 专辑 / 时长 / 状态 / 加入时间。

**2. 在 app 里点收藏，写到哪？** —— 这是这一版最重要的新概念。
平台的收藏夹是**别人的东西，只能读**。所以「可写」必须落在本地：
能力声明因此从「有没有收藏夹」长出了**读 / 写**这一维。来源页把三处说得明明白白：
本地收藏 `可读 ✓ 可写 ✓`，B 站与 YouTube `可读 ✓ 可写 ✗`。平台歌单页顶部有一条横幅直说：
「这是 B 站上的收藏夹，在这里只能读。你在 app 里点收藏会写进**本地收藏**；想让改动回到
B 站，要去它自己的收藏夹里改」+「复制为本地歌单」。

**3. 首选版本失效了怎么办？**
库里的歌**不会因为一个平台删了视频就消失**。状态列会显示 `已回退`（自动改用另一平台的版本
继续能听）或 `全部失效`（整行压暗、如实标出，而不是悄悄删掉）。点「来源」能看到为什么是这一版。

### 「来源默认不露」是怎么成立的

藏起来只有在**随时能问**的前提下才成立。所以右下角播放条和右栏都留了一个 `来源 ▸`，
点开是一张说明卡：正在播放的是哪一版、**为什么是这一版**（音质 › 已下载 › 可用性）、
这首歌的全部版本各自什么状态、以及「改用这一版 / 固定使用这一版」。回退的那首歌，
这张卡会直说「本来首选的是 B 站那一版，但它已经失效（条目已被 UP 主删除），所以自动换成了 YouTube」。

### 页面

| 页面 | 内容 |
|---|---|
| **我的歌**（主屏） | 统一库 + 筛选（全部 / 已下载 / 未下载 / 有问题的）+ 状态列 + 底部同步读数 |
| **歌单** | 4 个歌单：1 个本地（可写）、3 个是别处的收藏（只读）；点进去是歌单详情 + 只读横幅 |
| **最近播放** | 按天分组 |
| **已下载** | 按歌单分组（离线是照歌单消费的）+ 音频/歌词封面/上限三根电平块 + 「仅前半」警示 |
| **搜索** | 结果就是歌，和「我的歌」同一套行；已在库的没动作，不在库的那个动作是**加入我的歌** |
| **来源与同步** | 同步读数（新增/移除/合并/失败）、同步说明、三处收藏的**读写声明**与开关、接入来源 |
| **来源详情**（浮层） | 见上 |

### 与第 2 版的取舍

| 第 2 版 | 第 3 版 |
|---|---|
| 主屏 = 搜索结果 + 跨源去重开关 | 主屏 = 我的歌；去重变成看不见的基础设施 |
| 行内通道字母 `A` / `B` chip | 全部删掉，行里没有任何平台痕迹 |
| UP 主 / 播放量 / 合集时长 / bvid | 删除，换回 歌手 / 专辑 / 年份 |
| 队列行带通道 chip | 保留队列，去掉 chip，状态改为下载与可用性 |
| 能力声明集中在输入页 | 升级为**读/写声明**，落在来源与同步页 |
| 监听 / 队列 / 存储 / 输入 四个页面键 | 库导航：我的歌 / 歌单 / 最近播放 / 已下载 / 搜索 / 来源与同步 |

## 文件

- `ListenBli Aggregator.html` — 画布入口（base 样式、字体、载入顺序）
- `design-canvas.jsx` — 画布脚手架（来自 baoyu-design 的 `design-canvas.jsx`，未改动）
- `aggregator-data.jsx` — 多来源 mock 数据（含跨源重复项、缓存、会话、歌词出处）
- `aggregator-icons.jsx` — 方向无关的图标集
- `dir-a.css` / `dir-b.css` / `dir-c.css` — 三个方向各自的令牌与组件样式
- `direction-a.jsx` / `direction-b.jsx` / `direction-c.jsx` — 三个方向的聚合页
- `app.jsx` — 画布组装、对比表、`?only=` 路由
- `serve.mjs` — 零依赖静态服务器（见下）
- `screens/` — 状态截图：三个方向 × 合并/展开两态、方向对比表、整张画布，以及两版原型的每一页

第二阶段（方向 A 的深做）：

- `ListenBli Mixer.html` — 原型入口
- `mixer.css` — 原型外壳与四张新页面的样式（复用 `dir-a.css` 的令牌）
- `mixer-pages.jsx` — 队列 / 存储 / 输入 / 接入来源
- `mixer-app.jsx` — 外壳：页面键、快捷键、URL 参数

第三阶段（听歌 re-cut）：

- `ListenBli Library.html` — 当前版本的入口
- `library.css` — 库导航 / 统一歌曲行 / 歌单 / 已下载 / 来源与同步 / 正在播放 / 来源详情
- `library-pages.jsx` — 上述页面
- `library-app.jsx` — 外壳：库导航、点击即播放、快捷键与 URL 参数

> 共用组件的归置踩过一个坑：第 3 版用了 `.a-seg` / `.a-sw` / `.a-icobtn` / `.a-mtr`，
> 而这几个当时只写在 `mixer.css` 里，而 Library 页面并不加载它 —— 于是筛选器一直是无样式的。
> 两个交付物共享的东西（分段控件、开关、图标按钮、电平条、路径 chip）已经搬进 `dir-a.css`
> （方向 A 自己的样式表），`mixer.css` 只留 mixer 专有的类。

> `direction-a.jsx` 现在把它的子组件（`ATopBar`/`AInputRail`/`AResultList`/`ALyricFeed`/`ADeck` …）
> 导出到 `window`，原型是**组装**它们而不是复制一份 —— 否则两个交付物会各自漂移。
> `ATopBar` / `AInputRail` 也因此多了可选参数（`page` / `onPage` / `scope` / `onScope` / `onConnect`），
> 不传时行为与画布里完全一致。

## 怎么打开

多文件原型必须走 HTTP：`<script type="text/babel" src>` 在 `file://` 下会被浏览器拦截。

```bash
cd designs/listenbli-aggregator
node serve.mjs                     # → http://localhost:4319/listenbli-aggregator/ListenBli%20Aggregator.html
```

| 交付物 | URL |
|---|---|
| 三方向对比画布（阶段 1） | `/listenbli-aggregator/ListenBli%20Aggregator.html` |
| 混音台原型（阶段 2，已被取代） | `/listenbli-aggregator/ListenBli%20Mixer.html` |
| **聚合听歌 · 我的歌（当前）** | `/listenbli-aggregator/ListenBli%20Library.html` |

> 用 `node serve.mjs` 而不是 `python3 -m http.server`：Babel 是用 XHR 去取每个 `.jsx` 的，
> 一次加载会并发一串请求；标准库的 http.server 讲 HTTP/1.0 且不保持连接，在这种并发下会
> 偶发地把某个请求 reset 掉，丢掉 `app.jsx` 或 `direction-*.jsx` 就是一片空白且没有明显报错。
> `serve.mjs` 讲 HTTP/1.1、keep-alive、带 Content-Length，重载就稳了。

### 页面上的开关

**对比画布**

| 参数 | 作用 |
|---|---|
| 无 | 三个方向并排的画布（第一阶段的交付物） |
| `?merge=off` | 所有画板一进来就是**展开态**（合并重复 = 关），方便横比两种表达 |
| `?only=a` / `b` / `c` | 单独看某个方向，精确 1440×900，无画布外壳 |
| `?only=compare` | 单独看方向对比表 |

每个画板标题可点击进入全屏（←/→ 切换画板，Esc 退出）。

**混音台原型**

| 参数 | 作用 |
|---|---|
| 无 | 落在「监听」页 |
| `?page=mix\|queue\|disk\|input` | 直接落在某一页 |
| `?scope=all\|bilibili\|youtube` | 监听页的来源 tab |
| `?merge=off` | 监听页一进来就是展开态 |
| `?sheet=connect` | 直接打开「接入来源」浮层 |

**聚合听歌（当前版本）**

| 参数 | 作用 |
|---|---|
| 无 | 落在「我的歌」 |
| `?page=library\|playlists\|recent\|offline\|search\|sources` | 直接落在某一页 |
| `?playlist=<id>` | 打开某个歌单的详情（`default-fav` 是只读的那个） |
| `?sheet=source` | 打开来源详情浮层 |
| `?sheet=connect` | 打开接入来源浮层 |

键盘：`1`–`5` 切页面，`Esc` 关浮层。**点列表里任意一首歌，它就变成正在播放的那首** ——
这是整个布局围绕的唯一交互（试试点「夜曲」，右栏会显示已回退，再点 `来源 ▸` 看它为什么换了版本）。

键盘（阶段 2 原型）：`1`–`4` 切页面（就是四个页面键），`Esc` 关掉浮层。点击左侧通道条下方的四个页面键同样切换；
顶栏的 `CACHE` / `SOURCES` 两个读数块是「存储」「输入」的快捷入口；队列页的「下一首播放 / 移除」、
存储页的策略开关、输入页的作用范围与能力声明表都是**真的能点的**。

## 已经验证过的

两个交付物的**每一页**都按 **1440×900 精确落位**（`document.scrollWidth/Height` = 1440×900），
控制台只有 Babel 开发版提示、无错误。画布上三方向 × 两态、原型五页（含展开态与来源
作用域视图）都逐张截图审过，`screens/` 里就是审过的那些图。

修掉的真实缺陷（都是截图审出来的，不是靠猜）：

第一阶段：
- A/B 的进度条把手被 `overflow: hidden` 裁掉；
- A 的 `STREAMING` 与读数挤在一起；
- A 的歌词从第一行铺满导致底部截断 → 改为围绕当前行取窗口 + 两端渐隐；
- A 展开态承诺了「左侧竖线」但 CSS 里定义的是一个从未被使用的类名，实际没有线；
- B 把朱红用在了「无损音质」和注释记号上，违反它自己的颜色纪律；
- C 的「深度 = 缓存」编码太弱读不出来 → 加了行尾落盘进度列并加重了已缓存行的密度；
- C 展开态行高被一个 `display:flex` 的**行内** `<span>` 撑爆（块级 flex 会断行盒）；
- 对比表画板比内容高 60px，底部一片空白。

第三阶段：
- 库列表 11 首歌比可用高度高 27px、右栏歌词窗口太长、搜索结果 14 条溢出 → 行高与窗口调准；
- 「加入」按钮被塞进 28px 的列里挤到换行 → 动作列加宽到能放下一个按钮；
- `.a-seg` 的分段格子被 flex 压扁，四个筛选标签挤成一串（调音台那几处因为标签短没暴露）
  → `flex: none` + `nowrap`；
- **筛选器一直是完全没有样式的** —— 因为 `.a-seg` 定义在 `mixer.css`，而 Library 不加载它。
  这是最值得记的一条：共用组件必须住在共用样式表里；
- B 站收藏夹里出现了 YouTube 独有的《青花瓷》、YouTube 点赞里出现了 B 站独有的《稻香》
  → 按各平台实际持有的版本重排歌单，本地歌单才允许放任何歌；
- 歌单详情只列 3 首、下面空一大块 → 补足条目并加一行「Showing 7 of 128 / 加载更多」；
- 来源详情里把「这首歌的全部版本」写成了「这首歌唱片的全部版本」。

第二阶段：
- 加了四个页面键之后左侧通道条高出 13px 被裁掉 → 只在有页面键时收紧间距
  （用 `:has(.a-pages)`），画布上的排版一点没动；
- 缓存列表里两个同名的「夜曲」（不同来源）撞了 React key；
- 输入页写死了「未声明的 3 项」，而实际是 4 项 → 改成从能力声明里算；
- YouTube 的音质档位标签太长导致换行 → 把 itag 挪到备注里；
- 队列只有 6 行、缓存只有 8 行，列表底部空掉一大块 → 队列种子扩到 10 条、缓存扩到 11 条
  （没有编造新内容：队列条目、缓存条目的标题与来源都来自同一份 mock 世界）；
- 作用域视图的 meta 里「1 个来源」出现两次；
- 一个不可点击的状态机长成了按钮的样子 → 改成 tag；
- 队列/存储页的行内操作按钮 `opacity: 0` 只在悬停时出现，**截图里等于不存在** →
  改成常态 0.34、悬停到 1，这样审稿时看得见这些操作确实在。

## 两个阶段都不做

- 封面用单字字母版占位（沿用旧稿做法，接口接上 `Track.cover` 后替换 `Cover` 组件即可）。
- 数据是演示用 mock，形状对齐 `src/api/models.rs`；播放进度是纯前端时钟，不是真实音频。
- 不做真实音频、不做响应式（这是固定 1440×900 的桌面稿）。
- 设置面板（强调色 / 歌词字号 / 列表密度 / 中文字体）沿用旧稿已有设计，本方案没有重做。

## 下一步

设计侧完成了（当前版本请用 `ListenBli Library.html`）。往下走是**对 `src/` 的落地映射**，
把这份设计翻成 Rust/egui 的改动计划：

1. **来源抽象**：`enum Source` + 99 处 `match` → 一个 `Provider` 契约，能力声明即 trait 的
   可选面（`search` / `resolve` / `lyrics` / `session` / `library`）。这正是原型里
   「能力声明」那张表在代码里的对应物。
2. **模型**：`Track` 现在把 B 站 `bvid/cid/aid` 和 YouTube video id 塞进同一个 `bvid` 字段、
   靠 `source` 解释；需要拆成 `(provider, id, 附加键)`，并把 `AudioQuality` 里混装的
   B 站数字音质与 YouTube itag 换成每个来源自述的档位表。
3. **聚合与去重**：现在完全没有跨源合并。需要一份「同一录音」的判定与排序规则，
   以及用户在合并/展开之间的选择（原型里的那个开关）。
4. **缓存键**：`cache_key()` 目前按来源分叉（B 站用 `cid`、YouTube 用 video id），
   统一成 `(provider, id, quality)` 之后，存储页那套「完整 / 仅前半」的语义才成立。
5. **库与读写**：这是设计里最重的新东西。需要一个**本地库**（收藏/歌单/最近），
   平台收藏夹按**只读**同步进来、与本地条目做同一性合并；配置里要区分「别人家的收藏」与
   「我的收藏」。现在 `src/api/library.rs` 只有 B 站的收藏夹/历史，且是唯一数据源。
6. **UI 映射**：`src/ui/` 里哪块规到哪个面板、哪些设计令牌对应哪些配置项。当前主屏要从
   `ui_search_pane` 换成「我的歌」，右栏 `ui/lyrics.rs` 要扩成「正在播放 + 来源入口」。
